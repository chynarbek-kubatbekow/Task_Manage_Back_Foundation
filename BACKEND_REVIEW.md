# Проверка backend — 6 октября 2026

Проверены Django API, конфигурация Render, первоначальное создание компании, расписание и административный интерфейс. Изменения внесены локально. Предоставленный лог Render подтвердил сбой миграции `0004`: `cannot ALTER TABLE app_client because it has pending trigger events`. Исправлен порядок операций и выполнение отложенных проверок перед созданием индекса. Успешный повторный деплой самого сервиса ещё не подтверждён.

## Админка для управления фронтендом

Добавлены галочки включения разделов компании, проверка IANA timezone, сохранение wildcard и дополнительных прав ролей, удобные поля карточки пациента, неизменяемые номера пациентов/сотрудников и служебные поля записей. Записи можно отменять с сохранением истории. Сотрудники, пациенты, услуги, кабинеты и графики архивируются и восстанавливаются через массовые действия. Изменения и действия админки попадают в журнал; глобальное управление пользователями доступно только superuser.

API и административные формы используют одинаковые проверки графиков, отсутствий и занятости ресурсов. Административные роли учитываются только у активных пользователей с `is_staff`; обычный сотрудник продолжает работать через фронтенд.

## Проверки и границы результата

Проверки выполняются в отдельном окружении Python 3.11 с точными версиями из `requirements.txt`, без изменений исходного локального venv. Все 45 автоматических тестов проходят: HEAD/GET, отсутствие базы, SSL-редиректы, bootstrap, ограничения админки, API-права, переносы, графики, ресурсы, статусы, настройки, журнал удаления и обновление базы с существующими пациентами, сотрудниками и записями. Production smoke собирает WhiteNoise static, открывает форму входа админки с `DEBUG=False` и загружает CSS из manifest. `check --deploy`, `pip check` и проверка отсутствия новых миграций проходят.

Модельная схема не изменена: новые миграции для этих исправлений не требуются. Миграции при старте production оставлены в start command.

Локальные функциональные тесты используют SQLite. Дополнительно SQL миграции, сгенерированный PostgreSQL backend Django, проверен во встроенном [PostgreSQL PGlite](https://pglite.dev/docs/): существующие пациенты, сотрудник и запись, а также отложенный constraint trigger. Старый порядок воспроизводит ошибку pending trigger events; исправленный порядок вместе с выполнением отложенных проверок проходит. Это целевая SQL-проверка, а не полный запуск Django через PostgreSQL-драйвер. Проверки блокировок при одновременных запросах и запуск Gunicorn в Linux требуют staging/Render; они ещё не выполнены. Проверка production-конфигурации использует недоступную локальную PostgreSQL-заглушку и не обращается к рабочим данным. Работа размещённого сервиса и его фактические environment variables пока не проверены.

Дальнейшие улучшения: ограничение перебора пароля на auth endpoint; полноценный PostgreSQL integration job; контроль количества SQL-запросов для больших списков; объектные версии для защиты от перезаписи параллельных правок; более подробные изменения полей в журнале вместо только типа действия. Эти пункты не представлены как уже реализованные.

Настройка и диагностика сервиса: [DEPLOY_RENDER.md](DEPLOY_RENDER.md). Причина изменения блокировок: [Django QuerySet.select_for_update](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update).
